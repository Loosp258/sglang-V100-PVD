# PVD：独立小模型预测驱动的 KV 检索预取流水线
## 开发任务与交接规范——请求独立刷新版

若历史对话、旧任务文档与本文冲突，以本文明确确认的要求为准。
若当前代码与本文不同，必须区分“当前实现”和“目标实现”，
不得把规划中的功能描述为已经实现。

本文不意味着可以忽略仓库中的开发规范、安全约束或用户后续指令。

## 1. 最终目标

在现有 SGLang PVD 分离框架中实现：

D 使用独立小模型预测未来 token，仅用于提前生成检索需求；
V 根据检索 query 执行 CAGRA 搜索，将相关 Prompt KV 提前传回 D；
D 在继续正式 Decode 的同时，尽可能完成下一轮 KV 的检索与传输，
在刷新边界安全切换到下一轮 KV 工作集。

目标是减少刷新边界暴露出的等待时间，而不是仅提高搜索吞吐。

必须同时满足：
- 正式生成状态正确。
- KV 的逻辑位置和 attention 使用正确。
- RDMA 与 GPU 内存生命周期安全。
- 显存和在途任务数量有界。
- 允许近似推理，但需要量化生成质量退化。
- 性能收益必须通过端到端实验验证。

不能承诺“网络完全不可见”“输出完全无损”或“一定更快”。

## 3. 角色及数据归属

### P：Prefill
- 计算完整 Prompt KV。
- 向 Router 选定的 V group 上传。
- 保留现有上传确认和资源回收安全机制。

### V：KV 存储与检索
- 保存分配给它的请求的完整 Prompt KV。
- 建立请求内检索索引。
- 执行 CAGRA 搜索。
- 将选中 KV 交付给相应 D ranks。

### D：正式 Decode
- 使用目标模型生成正式 token。
- 管理当前 Prompt KV 工作集。
- 管理下一轮预取数据。
- 暂时保留所有正式生成 token 的 KV。
- 发起预测和预取，但不把预测 token 作为正式输出。

### Router
- 选择 P、V worker group、D。
- 将一致的关联信息传递给 P 和 D。
- 不负责每轮搜索、目标 GPU 地址或缓冲区分配。

一个请求归属选中的 V group。
一个 V group 可以服务多个 D，不要求永久一对一绑定。

“V 节点”“V worker group”“V rank/shard”不是同一概念。
不能因为加入 CAGRA，就默认将每个请求拆到多个 V group。

## 4. 用户已经确认的约束

### 4.1 预测
- 使用独立小模型预测未来 token。
- 预测仅服务于提前检索和 KV 预取。
- 预测 token 不输出给用户。
- 不推进正式 token 计数。
- 不写入目标模型已经确认的生成 KV。
- 不要求引入标准投机解码的 token 接受/拒绝流程。

### 4.2 近似
- 允许检索及稀疏 attention 带来的近似。
- 允许近似不等于允许位置错误、缺失内存读取、
  半完成 RDMA 读取或请求间数据混用。
- 必须评估质量与性能的权衡。

### 4.3 硬件
- 当前 V 只有 V100S。
- 必须以 V100S 为兼容性验证目标。
- 不得擅自改为“需要更新 GPU 才能运行”的完成方案。
- 如果确实无法实现，应报告阻断点并请用户决定，
  不能悄悄换算法或硬件后宣称完成。

### 4.4 刷新规则：这是本版最重要的约束
每个请求独立维护刷新时钟。

新请求加入 batch：
- 只触发新请求自己的首次 KV 初始化。
- 不强制旧请求刷新。
- 不重置旧请求的 M 计数。
- 不改变旧请求的刷新轮次。
- 不取消旧请求已在途的预测、检索或传输。
- 不能因为 batch 成员变化就判定旧请求的预取失效。

旧请求仅按自己的周期或明确的异常处理规则更新。

禁止恢复以下旧提案：
“新 req 加入时，batch 中所有 req 都进行 update。”

## 5. 当前实现基线：需要接手者再次核对

此前代码具有以下行为：

- 每个请求有 RefreshClock。
- 首次刷新必须执行。
- 此后根据该请求距离上次刷新已生成的 Decode token 数，
  判断是否达到 M。
- D 的正式 Decode 计数排除 P 采样的第一个输出 token。
- 到期请求单独进入刷新集合。
- TP ranks 对本轮刷新请求集合进行一致性协调。
- 刷新成功后才推进对应请求的时钟。
- 当前检索协议仅支持 full_prompt。
- 每次返回到期请求的完整 Prompt KV。
- 尚未完成 CAGRA 与预测预取流水线。
- 当前刷新路径有同步等待，可能阻塞当前 batch 的下一次 forward。

## 6. 每请求刷新与预取语义

### 6.1 计数定义

对请求 i：
- n_i：目标模型在 D 上正式生成的 token 数。
- M：刷新间隔。
- r：提前预取的步数。
- round_i：请求自己的刷新轮次。
- boundary_i：下一次要求安装新 KV 的正式 token 边界。

预测 token 不计入 n_i。

首次 KV 初始化成功后建立请求自己的周期。
其他请求加入、退出、结束，不改变该周期。

### 6.2 提前预取

在距离 boundary_i 还剩 r 个正式 token 时，
为该请求启动下一轮预测与预取。

必须区分：
- 预取已发起；
- 数据已到达；
- 数据可安全使用；
- 数据已安装为 active。

提前发起预取，不能提前将正式刷新时钟记为完成。
不能因为网络快或慢，悄悄改变刷新间隔的计数语义。

当前 begin/complete 若无法表达这种区别，应拆分状态，
而不是绕过 due 检查。

### 6.3 刷新边界

到达该请求的刷新边界时：
- 若 next KV 已安全就绪，则安装并推进该请求周期。
- 若未就绪，则等待或进入明确的失败处理。
- 不允许读取正在写入的 next buffer。
- 不允许无提示地继续跨过规定边界使用旧工作集。

### 6.4 当前等待策略

运行 batch 内已到刷新边界的请求仍可保留同步等待。
新请求的首轮准备必须在最终 `scheduler.waiting_queue` 异步进行，
完成安装及 ACK 后才进运行 batch，不加入旧请求的完成屏障。
实施约束和状态见 [首轮异步接入双语目标](../../PVD_Waiting_Queue_Bootstrap_CN_EN.md)。

注意：
“等待本轮到期请求”不等于“全 batch 都刷新”。

例如 M=16：
- A 距上次刷新生成 10 个 token：不刷新。
- B 生成 16 个 token：刷新。
- C 生成 3 个 token：不刷新。
- 新请求 D：首次初始化。

本轮 B 周期刷新与 D 首轮准备是两个独立路径。
A、C 的计数和预取状态不变；可以因 B 到期等待，不能仅因 D 初始化而等待。

周期刷新按请求异步放行仍是独立优化；新请求首轮异步接入已纳入本次目标。

## 7. 预测与 query 生成：必须解决的前置问题

独立小模型预测 token，不等于已经得到可检索目标模型 K 的 Q。

禁止：
- 直接默认小模型 Q 与目标模型 K 的向量空间兼容。
- 仅发送 token ID，却声称完成了 attention 向量检索。
- 将预测分支状态与正式生成状态混用。

接口开发时必须定义以下配置与校验；运行具体实验时才填入具体模型：
1. draft model 的用户自定义模型名称或本地路径，不内置指定模型白名单。
2. 可选 revision（分支/tag/commit）；不要求用户预先固定 revision，也不以缺省 revision 拒绝开发或加载。
3. tokenizer 与目标模型的兼容方式，以及 draft 的可配置运行位置和资源预算。
4. draft 如何与最新正式前缀重新对齐。
5. 预测覆盖哪些位置。
6. 如何生成目标检索空间的 query。
7. query 对应哪些 layer/head 和哪个刷新窗口。
8. 该过程增加多少计算、显存和同步成本。

用户已选择：小模型预测 token，目标模型独立 probe 路径生成 query。
不再因为具体模型尚未选定而阻止配置、provider 接口或测试开发。
自定义不等于任意架构自动受支持：在真正加载/启用时按模型架构、tokenizer、
Q 捕获能力、设备和预算校验。不兼容时明确报错，不隐式转换 token ID。
实际加载的模型标识、能取得的解析后 revision 和依赖版本写入实验记录。
本地模型没有可解析 revision 时标记未知/本地来源，不伪造版本，也不要求为了记录而下载或哈希全部权重。
这是复现记录，不是固定某个模型版本才能开发的门槛。
若实现需要未批准的额外训练或资源扩张，仍需先确认。

目标模型 probe 必须：
- 不改变正式输出、正式 KV、正式请求位置。
- 不推进正式采样器/RNG 状态。
- 清楚管理预测分支的临时 KV。
- 明确使用当前稀疏 KV 得到的 Q 仍存在近似误差。
- 不因额外计算吃掉收益而仍宣称完成性能目标。

## 8. V 侧索引与检索

### 8.1 检索范围

第一版只检索当前请求自己的 Prompt KV。

不得未经批准：
- 跨请求搜索并直接替换历史 KV。
- 跨不同模型、位置语义或上下文复用 KV。
- 引入跨 V group 的分布式搜索。

### 8.2 索引

索引数据、原始 KV、向量 ID 映射分别管理。

映射至少能定位：
Entry → layer → KV-head → 原始 token/page → 实际 KV 存储。

建立索引前必须确认：
- 上传已达到要求的原生传输终态。
- GPU 读取数据的顺序和可见性满足要求。

分别维护：
KV_STORED、INDEX_BUILDING、INDEX_READY、INDEX_FAILED。

完整 Prompt KV 不变时，索引可跨多个 Delivery 复用。
D 新生成 token 的 KV 暂不写回 V 索引。

索引粒度、距离度量及 query 处理必须有明确依据。
不同层/head 的分数不能未经定义直接混合比较。
不能把 cosine、原始点积或 page 代表向量视为无差别替换。

### 8.3 搜索结果

搜索输出不是裸地址，而是逻辑选择：
- Entry 和索引版本；
- layer/head 范围；
- 原始 token/page IDs；
- 有效长度；
- 返回数据布局；
- 需要的字节数。

可以将 token 候选映射成 pages 后去重传输。
page 扩张带来的额外字节和质量影响必须统计。

## 10. 接口约束

以下是语义要求，不强制使用这些字段名称。

### 10.1 PrefetchRequest
应绑定：
- 协议版本、检索模式；
- Entry/request/sequence ID；
- 请求刷新轮次；
- 正式前缀位置和目标刷新边界；
- 预测分支/query 版本；
- query 的 layer/head/位置语义；
- 检索及返回容量预算；
- 各目标 rank 的接收 descriptor；
- epoch、generation 和写入授权信息。

相同逻辑操作的重试必须可幂等处理。
不能对同一身份重复提交不受控的 WRITE。

### 10.2 SelectionResult
应包含：
- 索引版本；
- 逻辑 token/page 选择；
- layer/head 映射；
- payload 布局；
- 实际长度；
- 必要的有效位置元数据。

### 10.3 DeliveryResult
必须区分：
- 请求已受理；
- 搜索完成；
- WRITE 已提交；
- 原生传输完成；
- D 可安全读取；
- D 已安装/消费确认。

HTTP 返回成功不等于 RDMA 完成。
搜索完成不等于 KV 已到达。

### 10.4 TP 一致性
- ranks 对请求集合、轮次、失败路径保持一致。
- 各 rank 的地址、局部 heads 和 query 可以不同。
- 不得把合法的 rank-local 差异当作协议不一致。
- 不能让某个 rank 提前退出，造成其他 rank 卡在 collective。

### 10.5 布局
按实际 layer/head/token 所属关系路由，而非假设 rank 编号相等。
支持范围必须由实际代码和测试证明。
不支持的 TP、GQA/MQA 或布局组合应明确拒绝，不能错误重排。

## 11. D 的稀疏 KV 与缓冲区

必须配套修改 D，不能只减少 V 的发送量。

要求：
- 正确维护逻辑位置到物理 slot 的映射。
- 正确处理 attention mask、有效长度和位置编码语义。
- 组合检索 Prompt KV 与 D 正式生成 KV。
- 不读取缺失、旧轮次或未初始化数据。
- 更新 Prompt 工作集时不破坏生成 KV。

同时维护 active 与 next 的逻辑版本。
允许共享只读且安全固定的 pages，但禁止并发覆盖 active 数据。

资源预算必须包括：
- active/next Prompt 工作集；
- D 正式生成 KV；
- draft/probe 模型及临时 KV；
- V 原始 KV、索引和构建/搜索临时空间；
- gather/pack 和 RDMA staging；
- 在途及等待排空的资源。

有界 Prompt 工作集不意味着无限生成也不会 OOM：
D 的生成 KV 仍然增长，需要保留正常的容量与接纳限制。

首次初始化已确定为最终等待队列触发的完整 Prompt KV 异步交付，
经 registered staging + unpack 安装，而非直接写最终页。应报告峰值显存限制，
不能宣称已支持“Prompt 大到 D 从未装得下”的场景。

## 12. 预测偏差与错误处理

允许近似，但必须明确：
- 每轮使用哪些 query；
- 选中的 KV 用于哪个窗口；
- 是否保留初始/最近 token；
- 是否结合最近真实 Q 的候选；
- 预测偏差时是否进行补充检索；
- 搜索失败、索引未就绪和传输失败如何处理。

这些策略未确定前先提出方案，不自行隐藏决定。

token 预测匹配率不等于 KV 选择质量。
预测 token 不同也不代表所有预取 KV 无用。

近似策略的合法输出与协议错误必须分开：
- 相关性不够属于质量问题。
- 错 Entry、错位置、错轮次、读半完成数据属于正确性错误。

---

## 13. 传输生命周期安全

保留当前 Mooncake/PVD 已有的安全措施。

- 发布 descriptor 前预约容量并固定资源。
- 维护 Entry、索引、预测分支、Delivery、buffer 各自生命周期。
- 应用层 region/generation 不会自动成为 RNIC 的保护条件。
- 不能用应用层完成状态代替原生传输终态。
- 请求结束或取消不意味着 WRITE 停止。
- 关闭后续提交，确认已提交操作终态和 GPU 消费结束后，
  才能释放或复用空间。
- 无法确认完成时保持 draining/quarantine。
- 迟到的旧响应不能安装到新轮次。
- 新请求加入不能导致旧请求缓冲区身份被重用或失效。

不得为降低延迟而删除已有 MR、元数据一致性和 fence 保护。

## 14. 实施阶段

### 阶段 0：核对、可配置接口与状态机
交付：
- 基线 commit 和当前实现说明。
- 环境信息采集与独立 V100S CAGRA 实测工具；没有硬件时实测明确待验证。
- 可自定义 draft 模型名称/路径、可选 revision、运行位置/预算的接口设计。
- 固定的 query 路径：小模型预测 token → 目标模型独立 probe Q。
- 请求级刷新与预取状态机。
- 接口和显存预算。
- 未决问题清单及用户确认结果。

未通过硬件验证，不宣称 CAGRA 已可用，但可继续阶段 1–3 的通用实现及 CPU/fake 测试。

### 阶段 1：影子预测与检索
- D 正式生成仍走完整 KV 基线。
- 实际运行预测、query 生成和 V 检索。
- 不让选择结果影响正式 attention。
- 对照精确检索与真实 query 评估候选质量。
- 测量额外计算与搜索成本。

该阶段是诊断步骤，不改变最终的近似稀疏目标，
也不能宣称已经节省 D 的完整 Prompt KV 显存。

### 阶段 2：稀疏交付与 attention
- 实现选择结果、逻辑映射、pack、传输和安装。
- 验证 K/V 与源数据逐项对应。
- 接入稀疏 attention。
- 先使用同步刷新评估正确性与质量。

### 阶段 3：请求独立的提前预取流水线
- 在每请求的 M-r 位置触发。
- 实现 active/next 与安全切换。
- 预取与正式 Decode 重叠。
- 到 M 边界检查和等待。
- 新请求仅初始化自己，不干扰旧请求周期。
- 处理结束、取消、迟到和失败。

### 阶段 4：性能优化
- 调整 M、r、检索预算和并发限制。
- 优化打包、控制消息、提交与传输进度推进。
- 可以合并通信，但不能合并请求时钟。
- 不默认引入按请求异步放行或改变既定刷新规则。

每阶段分别记录“代码实现”“CPU/fake 验证”“真实 GPU/模型验证”。
硬件缺失不阻塞无依赖的后续开发，但不能标记实机阶段已验收，也不能默认启用未经验证的生产路径。

## 15. 验收标准

### 15.1 调度与状态
必须覆盖：
- 不同生成进度的请求共处一个 batch。
- 新请求加入，仅其首次初始化及原本到期者刷新。
- 新请求不重置旧请求计数。
- 新请求不取消旧请求在途预取。
- 预取提前完成，但未提前推进正式刷新时钟。
- 预取迟到，正确等待。
- 请求结束、EOS、取消和退出 batch。
- TP ranks 对状态一致。
- 多个 V groups 服务不同请求，但不产生全局刷新屏障。

### 15.2 数据与内存
必须验证：
- Entry/layer/head/token/page 对应正确。
- payload 边界与有效长度正确。
- active buffer 不被在途 WRITE 覆盖。
- 旧轮次结果不会安装。
- 生成 KV 不被 Prompt 更新损坏。
- 重试不会造成失控的重复写入。
- 超时和取消不会提前复用内存。
- 资源有界，容量不足时有背压或明确失败。

### 15.3 生成质量
与完整 attention 基线比较：
- 选定任务的质量指标；
- 必要时困惑度；
- 真实 query 下的检索召回；
- 预取有效率和补取率；
- 不同 M、r、检索预算的质量变化。

用户尚未指定可接受退化阈值：
实验前提出指标和阈值供确认，
不得自行宣布“质量可接受”或“无损”。

### 15.4 性能
至少比较：
1. 完整 KV 同步刷新基线。
2. 稀疏检索但无提前预取。
3. 最近真实 Q 驱动的提前预取基线。
4. 独立小模型预测驱动的提前预取。

记录：
- TTFT、TPOT p50/p95/p99、吞吐。
- 刷新边界的实际等待。
- draft/probe 计算开销及 GPU 竞争。
- V 排队、搜索、pack、传输、D 安装耗时。
- 实际网络字节、无用预取量。
- P/V/D 峰值显存。
- 稳定 batch 与持续新请求加入两类负载。

不能通过减少工作量、偷偷跳过规定刷新、
改变输出 token 统计或隐瞒质量退化来声称加速。

### 15.5 验证层级
明确区分：
- CPU 单元测试；
- mock/fake transport；
- 单 GPU 功能测试；
- 真实多 GPU/TP 测试；
- 真实多节点 Mooncake/RDMA 实验。

缺少哪一层就如实标记，不互相替代。

## 16. 明确的非目标

本任务不默认实现：
- 新请求加入导致旧请求全员刷新。
- batch 级统一 token 计数器。
- 预测 token 直接输出。
- 标准投机采样的接受/拒绝流程。
- 跨请求 KV 语义复用。
- 跨 V group 的全局 CAGRA 搜索。
- 任意 TP 组合自动兼容。
- D 生成 KV 持续回写 V。
- Host/NVMe 分层存储的完整产品化。
- 第一版按请求异步放行的调度重构。
- 为优化而更换整个通信栈。
- 未经确认的模型训练或额外硬件需求。

## 17. 不得猜测的事项

以下事项需要按层明确；不可再将未选具体模型当作通用开发阻断点：
- draft model 名称/路径、可选 revision、运行位置由用户在部署/实验时配置，不在代码中写死。
- 目标检索 query 使用已确认的目标模型独立 probe；具体架构适配在加载时校验。
- 索引粒度及跨层/head 的选择策略。
- 索引未就绪时的周期检索策略。
- 首轮初始化已确定（2026-09-19）：由 Decode 把请求放入最终等待队列
  （`scheduler.waiting_queue`）作为触发点，再由 D 发起完整 Prompt KV 拉取，
  目标为该请求已预分配的最终 KV 页；传输仍由 V 执行获授权的 RDMA WRITE，
  不引入 RDMA READ。请求在等待队列内标记 not-runnable，安装校验通过后才入运行 batch。
  待设计项仅剩：not-runnable 门控的具体实现与并发拉取请求之间的公平接纳策略。
- 预测偏差、搜索失败和传输失败的处理策略。
- 可接受的质量退化阈值。
- 真实实验环境的依赖与资源上限在实机验收时记录并验证。

可配置参数不必全部由用户手工指定，
但默认值必须有依据，并明确标为可调默认值，
不得把未经确认的架构决定伪装成普通参数。

遇到无法从代码或本文确定的实质性设计问题：
先报告事实、给出选项，再询问用户。
不要按个人偏好重新定义最终目标。
