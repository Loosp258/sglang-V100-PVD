# PVD 3.0 设计依据（用户已确认）

## 目标和边界

Router 同时选择 P、V group、D，以统一 transfer/request ID 关联三方，并把 V group ID 发给 P、D。V 注册 Router 分发的请求；精确 KV 内存大小及布局由 P tokenize 后的 manifest 确定，V 返回已注册接收区域。

P 保存完整 Prompt KV 到 V。V 接收并提交所有 shard 后为 KV_READY（现有协议 STORED），不实现图中步骤 7 的索引构建和步骤 12 的 CAGRA search。D 等待 KV_READY 后进入 waiting queue；continuous batching 选中后，首次以及每生成 M 个 Decode token 后向 V 发送序列 ID 列表、独立 delivery ID、Mooncake session 和接收区域。每次回传完整 Prompt KV。

D 生成的 KV 暂时常驻 D，不回写 V。D 复用接收 staging；只覆盖 Prompt 的有效 token，即使最后一页包含生成 token，也不能覆盖生成部分。Entry、EntryShard、Delivery 生命周期保持独立，同一 Entry 支持多个 Delivery。

## 实现约定

- `--pvd-kv-refresh-interval` 指定 M，默认 16，必须为正整数；P 产生的首 token 不计入 D 的 M。
- 保留当前 P TP1/2、每 V group 两个 storage shards、D TP2/4 和 single-rail debug 支持；不扩大硬件拓扑范围。
- Router 使用现有 round-robin V group 选择与可信 ID/URL 注册表；新增 V request admission 控制接口。发送 prompt 的原始请求形态作为 admission 元数据，不执行 tokenizer 或索引。
- 精确空间预留由 P manifest 驱动；V 无模型，因此不能仅根据原始文本准确预留字节数。
- D admission 只等待 STORED 和首 token 元数据，真正传输放到已选 batch 的 Decode 执行前。
- 第一版使用同步的 batch KV 更新屏障，关闭 D overlap scheduling，确保旧 forward 完成后再更新 KV；不宣称隐藏网络延迟。V group 间控制请求可并发，各 TP rank 对成功/失败形成一致结论。
- 首次获取后，每 M 个已完成 D Decode token 更新一次。每轮独立 delivery ID，验证回复身份、选择模式和 token 范围；只有回传、GPU 回填及 ACK 成功才推进轮次。
- 扩展点为显式 `full_prompt` selection 和逻辑 token 范围；未来可以新增稀疏选择，不将未实现的搜索伪装为已有能力。
- V Entry 使用可续期 consumer lease 防止长 Decode/排队期间 TTL 回收；D 完成/取消释放自己的 lease，Entry 可保留至缓存 TTL，不删除其他 consumer 数据。
- 失败后不使用旧/未完成 KV 执行 forward；清理传输必须先确认远端停止写入，之后才能释放接收内存。

## 验证与限制

CPU fake transport 验证完整字节回传、多轮及多序列、lease/TTL、异常输入和幂等；CPU tensor 测试验证尾页生成 KV 不被覆盖。Scheduler adapter 测试验证入队不传 KV、首次/每 M token 更新、多个 rank 一致处理及 cleanup。Rust Gateway 测试验证三方请求身份；真实 CUDA/Mooncake 和三机器 benchmark 需在 RDMA 硬件上验证。

此阶段 D 仍需容纳完整 Prompt KV、生成 KV 和一个接收 staging。周期性重传用于打通扩展流程，不带来显存节省。
