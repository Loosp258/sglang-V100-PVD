# PVD 3机器6卡V100S操作指南

本文给出从 CloudLab 节点启动后开始，到 P、V、D、Gateway 启动、正确性检查和 benchmark 的完整操作流程。

本文固定使用以下实现版本：

```text
Repository: https://github.com/Loosp258/sglang-V100-PVD
Branch:     pvd-disaggregation
Commit:     bb8918828
```

不要使用 PyPI 上的普通 `sglang-router`。PVD Gateway 必须由上述源码构建，因为 PVD ID 注入、V 健康检查和 single-rail debug 校验都在这个分支中。

## 1. 固定拓扑

| CloudLab 节点 | PVD 角色 | 服务地址 | GPU |
| --- | --- | --- | --- |
| `node-0` | P / Prefill | `10.0.1.1:30000` | GPU 0、1，TP=2 |
| `node-1` | V rank0、V rank1、Gateway | V coordinator `10.0.1.2:9000`；Gateway `10.0.1.2:8000` | V0=GPU 0，V1=GPU 1 |
| `node-2` | D / Decode | `10.0.1.3:30001` | GPU 0、1，TP=2 |

当前 CloudLab 只有 `mlx5_0` 具备物理 carrier：

```text
mlx5_0 / eno33np0: ACTIVE，25 GbE，可用 RDMA
mlx5_1 / eno34np1: NO-CARRIER，不能用于 RDMA
```

因此使用显式 single-rail debug 映射：

```text
P0 -> V0 -> D0: mlx5_0
P1 -> V1 -> D1: mlx5_0
```

所有 P、V、D 命令都必须使用：

```bash
--pvd-rank-rails mlx5_0,mlx5_0
```

该模式保留两个 rank 的独立 GPU shard，但没有双 rail 聚合带宽或链路冗余。

## 2. 端口和终端安排

确保节点之间允许访问以下端口：

| 端口 | 所在节点 | 用途 |
| ---: | --- | --- |
| 8000 | node-1 | Gateway 对外服务 |
| 9000 | node-1 | V rank0 coordinator |
| 9200 | node-1 | V rank0 shard API |
| 9201 | node-1 | V rank1 shard API |
| 30000 | node-0 | Prefill 服务 |
| 30001 | node-2 | Decode 服务 |

建议打开五个长期终端：

1. node-1：V worker group 和 coordinator
2. node-0：P
3. node-2：D
4. node-1：Gateway
5. node-1：健康检查和 benchmark

启动顺序必须是：

```text
V worker group -> P 和 D -> Gateway -> 正确性测试 -> benchmark
```

## 4. V 容量配置

本指南固定模型为：

```text
/proj/edgecut-PG0/models/Qwen2.5-7B-Instruct
dtype=float16
TP=2
page_size=16
```

Qwen2.5-7B 每个 rank 的 KV page 字节数为：

```text
2 × 28 layers × 2 KV heads/rank × 128 head_dim × 2 bytes × 16 tokens
= 458752 bytes
```

正式 benchmark 推荐每个 V rank 使用：

```text
PAGE_BYTES=458752
TOTAL_PAGES=50000
GPU pool 大小约 21.36 GiB/rank
```

这适合 32 GiB V100，并为 CUDA/Mooncake 上下文保留约 10 GiB 空间。若实际 GPU 上还有其他进程，应先查看 `nvidia-smi` 并相应减小 `TOTAL_PAGES`。

附件中原来的 `128 pages × 1 MiB` 只适合一两个 smoke 请求，不能直接跑完整 sweep。Entry 默认保留 300 秒，过小的 V pool 会很快出现 page allocation/capacity 错误。

## 5. 终端 1：单进程启动完整 V worker group

登录 node-1：

```bash
ssh node-1

source ~/miniconda3/etc/profile.d/conda.sh
conda activate sglang-v100
cd ~/cloudlab-stack/src/sglang-V100-PVD

export PVD_ROOT=/proj/edgecut-PG0/${USER}-pvd
unset MC_FORCE_TCP
export MOONCAKE_PROTOCOL=rdma
sudo modprobe nvidia_peermem
```

一条命令同时启动 V0、V1 和 coordinator：

```bash
CUDA_VISIBLE_DEVICES=0,1 \
python -m sglang.srt.disaggregation.pvd.server \
  --world-size 2 \
  --host 0.0.0.0 \
  --advertise-host 10.0.1.2 \
  --coordinator-port 9000 \
  --shard-port-base 9200 \
  --pvd-rank-devices 0,1 \
  --pvd-rank-rails mlx5_0,mlx5_0 \
  --transfer-backend mooncake \
  --strict-rdma-preflight \
  --total-pages 50000 \
  --page-bytes 458752 \
  2>&1 | tee "${PVD_ROOT}/logs/vector-group.log"
```

`--pvd-rank-devices 0,1` 使用的是进程内 CUDA 设备编号：V0 绑定 `cuda:0`，V1 绑定 `cuda:1`。`--total-pages` 是每个 V shard 的容量，不是两个 GPU 的合计容量。

不要关闭该终端。它退出时两个 V shard 和 coordinator 会一起停止。另开终端检查：

```bash
ss -lntp | grep -E '9000|9200|9201'
curl -s http://10.0.1.2:9200/internal/health | python -m json.tool
curl -s http://10.0.1.2:9201/internal/health | python -m json.tool
curl -s http://10.0.1.2:9000/health | python -m json.tool
```

两个 shard 的健康结果分别应包含 `rank: 0` 和 `rank: 1`，并都显示：

```text
rail: mlx5_0
rail_mode: single-rail-debug
rail_present: true
active_port: true
gpu_memory_registered: true
local_gpu_transfer: true
```

Coordinator 的 `healthy` 应为 `true`，并且两个 shard 都应显示 `rail=mlx5_0` 和 `rail_mode=single-rail-debug`。

如需回退到旧的双进程诊断模式，仍可显式传入 `--rank 1` 和 `--rank 0 --rank1-shard-url ...`；正常部署不要传 `--rank`。

## 8. 终端 4：构建并启动 Gateway

Gateway 运行在 node-1，不占用 V 的 GPU：

```bash
ssh node-1

source ~/miniconda3/etc/profile.d/conda.sh
conda activate sglang-v100
cd ~/cloudlab-stack/src/sglang-V100-PVD/sgl-model-gateway

export PVD_ROOT=/proj/edgecut-PG0/${USER}-pvd
```

如果还没有 Rust 工具链，先安装可用的稳定版 Rust/Cargo；然后从当前分支构建，不要安装 PyPI Router：

```bash
cargo build --release --bin smg
./target/release/smg --version-verbose
```

启动 Gateway：

```bash
./target/release/smg launch \
  --host 0.0.0.0 \
  --port 8000 \
  --pvd-disaggregation \
  --pvd-vector-coordinator-url http://10.0.1.2:9000 \
  --prefill http://10.0.1.1:30000 none \
  --decode http://10.0.1.3:30001 \
  --log-level debug \
  2>&1 | tee "${PVD_ROOT}/logs/gateway.log"
```

Gateway 不需要额外的 rail 参数。它会读取 V coordinator 的健康报告，只接受以下两种映射：

```text
生产：mlx5_0,mlx5_1
调试：mlx5_0,mlx5_0
```

当前模式应输出 single-rail debug 警告，而不是启动失败。

### 8.1 扩展 P 和 D 节点池

V coordinator 不绑定某一个 P 或 D 地址。需要增加节点时，分别重复传入 `--prefill` 或 `--decode`：

```bash
./target/release/smg launch \
  --host 0.0.0.0 \
  --port 8000 \
  --pvd-disaggregation \
  --pvd-vector-coordinator-url http://10.0.1.2:9000 \
  --prefill http://10.0.1.11:30000 none \
  --prefill http://10.0.1.12:30000 none \
  --decode http://10.0.1.21:30001 \
  --decode http://10.0.1.22:30001 \
  --prefill-policy round_robin \
  --decode-policy power_of_two
```

P 节点数和 D 节点数相互独立；每个请求只选择其中一个健康 P worker 和一个健康 D worker。这里的一个 URL 表示一个完整的 SGLang worker group，该 group 内部仍可包含多个 TP rank。当前 PVD v1 数据布局要求所有候选 P/D group 使用相同模型、revision、KV dtype、page size 和 TP=2；PVD 2.0 的异构 TP 重分片不包含在本次单进程 V 启动改造中。

## 9. 终端 5：正确性测试

登录 node-1：

```bash
ssh node-1

source ~/miniconda3/etc/profile.d/conda.sh
```

发送一个确定性请求：

```bash
curl -s http://10.0.1.2:8000/generate \
  -H 'Content-Type: application/json' \
  -d '{
    "text": "PVD_TEST_001: Explain GPU RDMA in one sentence.",
    "sampling_params": {
      "temperature": 0,
      "max_new_tokens": 32
    }
  }' | python -m json.tool
```

然后检查各角色日志：

```bash
grep -Ei \
  'PVD_TEST|pvd_transfer_id|pvd_delivery_id|transferSync|RDMA' \
  "${PVD_ROOT}/logs/prefill.log" | tail -50

grep -Ei \
  'PVD_TEST|pvd_transfer_id|pvd_delivery_id|RDMA ready|Finish:' \
  "${PVD_ROOT}/logs/decode.log" | tail -50

grep -Ei \
  'transferSync|openSegment|RDMA ready|rdma' \
  "${PVD_ROOT}/logs/vector-group.log" | tail -100
```

正确结果应同时满足：

- Gateway 返回正常生成文本。
- P 收到 Gateway 注入的 `pvd_transfer_id` 和 `pvd_delivery_id`。
- P 的两个 TP rank 把完整 prompt KV 写入对应 V shard。
- D 的两个 TP rank 收到 RDMA ready/Delivery 完成信息并正常 decode。
- V rank0 和 rank1 都使用 `mlx5_0`，且没有访问 `mlx5_1` 的失败。

## 13. 并发 Sweep：1、2、4、8、16、32

```bash
source ~/miniconda3/etc/profile.d/conda.sh
conda activate sglang-v100
cd ~/cloudlab-stack/src/sglang-V100-PVD

export HF_HOME=/proj/edgecut-PG0/${USER}-hf-cache
export HF_HUB_CACHE=${HF_HOME}/hub
export HF_DATASETS_CACHE=${HF_HOME}/datasets
export BENCH_DIR=/proj/edgecut-PG0/${USER}-pvd/bench

mkdir -p "${BENCH_DIR}"

for C in 1 2 4 8 16 32; do
  N=$((C * 10))
  if [ "${N}" -lt 20 ]; then
    N=20
  fi

  echo
  echo "========================================"
  echo "PVD BENCHMARK"
  echo "Concurrency : ${C}"
  echo "Requests    : ${N}"
  echo "Input       : 1024 tokens"
  echo "Output      : 128 tokens"
  echo "========================================"

  python -m sglang.bench_serving \
    --backend sglang \
    --base-url http://10.0.1.2:8000 \
    --model /proj/edgecut-PG0/models/Qwen2.5-7B-Instruct \
    --tokenizer /proj/edgecut-PG0/models/Qwen2.5-7B-Instruct \
    --dataset-name random \
    --num-prompts "${N}" \
    --random-input-len 1024 \
    --random-output-len 128 \
    --random-range-ratio 1 \
    --max-concurrency "${C}" \
    --request-rate inf \
    --warmup-requests 2 \
    --tokenize-prompt \
    --output-file "${BENCH_DIR}/concurrency-${C}.jsonl" \
    --output-details \
    2>&1 | tee "${BENCH_DIR}/concurrency-${C}.log"

  echo "===== concurrency=${C} FINISHED ====="
  sleep 10
done
```

参数含义：

- `--request-rate inf`：客户端尽快提交请求。
- `--max-concurrency C`：限制同时在执行的请求数。
- 这里的 concurrency 是不同并发负载，不是固定某次 GPU forward 的 batch size。

## 15. 常见问题

### 15.1 启动仍然检查 mlx5_1

确认三个节点和 Gateway 都使用至少包含提交 `bb8918828` 的代码，并确认 P、D、V0、V1 都传入：

```bash
--pvd-rank-rails mlx5_0,mlx5_0
```

不要混用旧 V 进程或旧 Gateway binary。代码更新后必须重新执行：

```bash
cd ~/cloudlab-stack/src/sglang-V100-PVD/sgl-model-gateway
cargo build --release --bin smg
```

### 15.2 Gateway 拒绝 V 健康检查

检查：

```bash
curl -s http://10.0.1.2:9000/health | python -m json.tool
```

两个 shard 必须都是：

```text
rail=mlx5_0
rail_mode=single-rail-debug
rail_present=true
active_port=true
gpu_memory_registered=true
local_gpu_transfer=true
```

### 15.3 出现 page allocation 或 capacity 错误

检查 V 启动参数和显存：

```bash
nvidia-smi
grep -Ei 'capacity|allocation|page|expired|released' \
  /proj/edgecut-PG0/${USER}-pvd/logs/vector-group.log | tail -100
```

`128 pages × 1 MiB` 是 smoke 配置，不足以完成本指南的 sweep。优先使用 `50000 × 458752 bytes`；如果显存不足，应降低 `TOTAL_PAGES`，同时减少请求数或等待 Entry TTL 回收后再跑下一组。

### 15.4 Mooncake 意外走 TCP

检查：

```bash
echo "MC_FORCE_TCP=${MC_FORCE_TCP-<unset>}"
echo "MOONCAKE_PROTOCOL=${MOONCAKE_PROTOCOL-<unset>}"
```

正确设置：

```bash
unset MC_FORCE_TCP
export MOONCAKE_PROTOCOL=rdma
```

日志中应看到 RDMA transport，而不是 TCP transport。

### 15.5 P/D layout 不一致

平衡 TP2 部署时确认 P 和 D 完全一致：

```text
model path
model revision
dtype=float16
TP=2
page_size=16
attention backend
pvd-model-instance-id=qwen25-7b-pvd
pvd-rank-rails=mlx5_0,mlx5_0
```

PVD 2.0 的异构 TP 路径允许 P 和 D 的 `TP` 不同，但 model path、model
revision、dtype、page size、attention backend、总 KV head 数量及
`pvd-model-instance-id` 仍必须一致。

### 15.6 PVD 2.0：P TP1、V TP2、D TP4

PVD 2.0 首个异构 TP 组合为：

```text
P0 -> V0 + V1
V0 -> D0 + D1
V1 -> D2 + D3
```

P 使用一张 GPU：

```bash
CUDA_VISIBLE_DEVICES=0 \
python -m sglang.launch_server \
  --model-path "${MODEL}" \
  --dtype float16 \
  --tp-size 1 \
  --disaggregation-mode prefill \
  --disaggregation-transfer-backend mooncake \
  --disaggregation-topology pvd \
  --pvd-vector-coordinator-url http://10.0.1.2:9000 \
  --pvd-model-instance-id qwen25-7b-pvd \
  --pvd-rank-rails mlx5_0
```

D 使用四张 GPU：

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 \
python -m sglang.launch_server \
  --model-path "${MODEL}" \
  --dtype float16 \
  --tp-size 4 \
  --disaggregation-mode decode \
  --disaggregation-transfer-backend mooncake \
  --disaggregation-topology pvd \
  --pvd-vector-coordinator-url http://10.0.1.2:9000 \
  --pvd-model-instance-id qwen25-7b-pvd \
  --pvd-rank-rails mlx5_0,mlx5_0,mlx5_0,mlx5_0
```

V 仍按第 5 节用一个进程管理两张 GPU，不需要改变 `PAGE_BYTES`。
此组合要求 D 所在物理节点至少有 4 张 GPU；本指南原始的“每节点 2 卡、共
6 卡”硬件不能直接运行 D TP4，只能运行平衡 TP2。异构路径目前只支持普通
MHA/GQA，且总 KV head 数必须能被 4 整除；MLA、MQA head replication、SWA
和辅助状态缓存会在传输前被拒绝。

## 16. 停止顺序

每个长期终端使用 `Ctrl+C` 正常停止。建议顺序：

```text
Gateway -> P -> D -> V worker group
```

不要在仍有 Delivery 执行时直接终止 V。
